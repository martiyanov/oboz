# Ресурсоёмкость «Обозревателя» на ВДС

Замеры сделаны **8 ноября 2026** на вашем ВДС: 4 vCPU, 7.8 ГБ RAM, диск 89 ГБ (свободно ~22 ГБ),
Ubuntu 22.04, Node.js 24.22, сервис `oboz-web` (веб-версия) + nginx. CLI/TUI на сервере не
запущены; `oboz watch` по таймеру не настроен.

## Коротко

| Ресурс | Что занимает | Доля ВДС |
|---|---|---|
| **RAM** | 110–185 МБ в покое, до 270 МБ в пике | **1.4–3.5 %** от 7.8 ГБ |
| **CPU** | ~0.6–0.7 % одного ядра в простое; 3–6 % одного ядра при активном выборе фильтров; пики 1.2–11 с на холодный пересчёт | **0.2–1.5 %** от 4 vCPU |
| **Диск** | 6.3 МБ код+документация, 3.9 МБ кэш лент, 0.1 МБ прочее | **<0.02 %** от 89 ГБ |
| **Сеть (главное)** | ~180–200 МБ/сутки при `cacheTtlSec=1800` | **~5.5–6 ГБ/месяц** входящего |
| **Трафик клиентам** | ~31 КБ gzip первая загрузка, ~11.5 КБ на автообновление | зависит от числа открытых вкладок |

Вывод: по CPU/RAM/диску сервис почти незаметен, основной постоянный расход — **входящий трафик
RSS-лент**. Его можно уменьшить в 2–6 раз настройкой `cacheTtlSec` (см. ниже), почти без потери
актуальности для часового обзора.

## 1. Память

| Что | Значение |
|---|---|
| RSS процесса (покой/после старта) | 110–185 МБ |
| cgroup `MemoryCurrent` после старта | ~61 МБ |
| cgroup `MemoryCurrent` после серии фильтров/сборок | ~240 МБ |
| Пик (`MemoryPeak`/`VmHWM`) | ~270 МБ |
| Потоков | 11 |

Кэши ограничены: digest-кэш — 32 записи, кэш досье — 32 записи (LRU по времени), статика —
несколько файлов. Утечек нет, но при интенсивном выборе фильтров память кратковременно растёт
из-за одновременных сборок. Для тарифа 8 ГБ это несущественно; ориентир для меньшего ВДС —
256–320 МБ.

## 2. CPU

Замеры:

- **Один пересчёт сводки** (`buildDigest`, ленты уже в кэше): **1.0–1.3 с CPU**, ~0.7–1.2 с
  реального времени. При 32 лентах это кластеризация ~1200 публикаций и оценка ~1000 событий.
- **Холодный пересчёт** (первый после рестарта/обновления лент): до **11 с** (наблюдался максимум
  11 032 мс: скачивание 32 лент + первый расчёт). Прогрев запускается автоматически при старте,
  поэтому первый посетитель обычно уже не ждёт.
- **Простой** (только фоновый прогрев раз в ~3 минуты): 20–26 с CPU/час ≈ **0.6–0.7 % одного
  ядра**.
- **Активное листание фильтров** (каждая новая комбинация регион/порог/тема/город — отдельная
  сборка): наблюдалось ~100 сборок/час ≈ 100 с CPU/час ≈ **2.8 % одного ядра**; в замере с живым
  трафиком — 12.6 с CPU за 210 с ≈ **6 % одного ядра** (1.5 % от 4 vCPU).
- **HTTP-запросы**: `/healthz` ≈ 1 мс CPU, кэшированный `/api/digest` ≈ 2 мс CPU. 50 запросов
  подряд — 421 мс реального времени, 100 мс CPU.

То есть даже при активном использовании сайт не мешает остальным сервисам на 4-ядерном ВДС;
дорогие операции — только уникальные пересчёты, они кэшируются.

## 3. Сеть

### Входящий трафик лент

- 32 RSS-ленты, суммарный размер одного полного скачивания — **3.72 МБ** (без HTTP-заголовков).
- Сейчас **`cacheTtlSec = 1800`** (обновлено 8 ноября 2026): ленты скачиваются примерно
  **раз в 30 минут**, т.е. **~48 раз в сутки** → **~3.72 МБ × 48 ≈ 178 МБ/сутки** →
  **~5.5–6 ГБ/месяц** с учётом HTTP-заголовков/TLS.
- До этого стояло 300 с; замеренный тогда интервал между полными скачиваниями был **306 секунд**
  (14:17:27 → 14:22:33), т.е. ~280 раз в сутки и ~30–33 ГБ/месяц. Именно поэтому TTL поднят.
- **Проверено на проде:** после включения 1800 с файлы кэша лент не обновлялись 6+ минут, пока
  сводка пересчитывалась по расписанию — то есть скачивание действительно раз в 30 минут, а не
  каждые 5. TTL виден в `/healthz` → `resources.feedCacheTtlSec`.
- Самые тяжёлые ленты: Meduza 425 КБ, «Время Н» 360 КБ, Soyuz 313 КБ, НИАНН 289 КБ,
  «Коммерсантъ» 265 КБ, iXBT 223 КБ, РБК 216 КБ.

### Что с этим делать

| `cacheTtlSec` | Скачиваний/сутки | Трафик/месяц | Задержка свежести ленты |
|---|---|---|---|
| 300 | ~280 | ~30–33 ГБ | до 5–7 мин |
| 600 | ~140 | ~15–16 ГБ | до 10–12 мин |
| 900 | ~95 | ~10–11 ГБ | до 15–18 мин |
| **1800 (сейчас)** | **~48** | **~5.5–6 ГБ** | **до 30–35 мин** |
| 10800 (3 часа) | ~16 | ~1.8–2 ГБ | до 3–3.5 ч |

Для часового обзора задержка ленты до 30 минут нормальна: сводка всё равно пересчитывается из
кэша каждые ~3 минуты, а важные события почти всегда имеют несколько публикаций в течение
первого часа. Если хотите ещё экономнее — `cacheTtlSec: 10800` (3 часа) даёт ~2 ГБ/месяц, но
тогда при часовом `oboz watch` вы будете видеть ленту с задержкой до 3 часов.

### Трафик клиентам

- Первая загрузка страницы (gzip): HTML 3.5 КБ + JS 17.8 КБ + CSS 8 КБ + тема ~1.5 КБ ≈ **31 КБ**.
- Ответ `/api/digest` (12 событий, gzip): **11.5 КБ**; без gzip — 78 КБ.
- Автообновление раз в минуту: 11.5 КБ/мин ≈ **690 КБ/час на открытую вкладку**; 8 часов
  открытой вкладки ≈ 5.5 МБ (в обе стороны примерно поровну).
- 1000 просмотров в сутки ≈ **45 МБ/сутки** исходящего; это меньше, чем трафик лент.

## 4. Диск

| Каталог | Размер |
|---|---|
| Код + документация + скриншоты | 6.3 МБ (из них скриншоты 1.9 МБ) |
| `.cache/rss` (32 XML) | 3.8 МБ |
| `.cache/wiki` (16 файлов) | 68 КБ |
| `.state` (обратная связь, seen, логи) | ~4 КБ |
| Журнал systemd (весь сервер) | 712 МБ, из них логи `oboz-web` — ~250 строк/час |

Кэш лент перезаписывается, а не растёт. Wiki-кэш пока маленький, но файлы живут дольше TTL 24 ч
и не удаляются — рекомендуется раз в месяц чистить старые файлы (или добавить автоочистку), чтобы
через год не накопить десятки мегабайт. Всё остальное — мегабайты.

## 5. CLI/TUI и `watch`

- Разовая команда `./oboz news` — та же сборка ~1 с CPU и 3.72 МБ трафика (если кэш устарел).
- `oboz watch --every 60m` в фоне — один цикл в час: ~24 сборки/сутки → **~90 МБ/сутки** трафика
  (2.7 ГБ/месяц) и ~24 с CPU/сутки. Легче постоянно работающего веб-сервера.
- `oboz feedback` — чтение файла, ресурсов не требует.

## 6. Как самостоятельно проверять

```bash
# память/CPU/статус
systemctl show oboz-web -p MemoryCurrent,MemoryPeak,CPUUsageNSec,MemoryCurrent,TasksCurrent
ps -o pid,rss,%cpu,etime,cmd -p "$(systemctl show oboz-web -p MainPID --value)"

# новые метрики ресурсов в healthz
curl -s https://agonarena.ru/oboz/healthz | jq '.resources, .stats'

# размеры кэшей и диска
du -sh /home/openclaw/oboz/.cache/rss /home/openclaw/oboz/.cache/wiki /home/openclaw/oboz/.state
ls /home/openclaw/oboz/.cache/rss | wc -l

# сборки и их длительность
sudo journalctl -u oboz-web --since '-1 hour' | grep 'built in'
```

В `/healthz` теперь есть блок `resources`: RSS, heapUsed, размеры кэшей и число сохранённых
отзывов.

## 7. Рекомендации

1. **Трафик:** уже сделано — `cacheTtlSec=1800` (30 минут), расход лент ~5.5–6 ГБ/мес вместо
   ~30–33 ГБ. Если нужен ещё меньший расход, поставьте `10800` (3 часа): ~1.8–2 ГБ/мес, но
   свежесть ленты будет до 3 часов.
2. **CPU при кликах по фильтрам:** сейчас каждая комбинация «регион+порог+тема+город» делает
   отдельный пересчёт (~1.2 с CPU). Раз в бэклоге — OBS-002: строить базовую сводку на
   регион+порог и фильтровать темы/города в памяти; это снизит интерактивный CPU в 5–10 раз.
3. **Wiki-кэш:** добавить автоочистку файлов старше 30 дней (сейчас растёт медленно).
4. **Если трафик критичен:** отключить самые тяжёлые ленты (`enabled: false` в `sources.json`) —
   например, Meduza/Время Н/Soyuz дают ~1 МБ из 3.7 МБ.
5. **Мониторинг:** `/healthz` (ресурсы), `systemctl status oboz-web`, `journalctl -u oboz-web`;
   аварийный лимит памяти при желании: `Environment=NODE_OPTIONS=--max-old-space-size=256`.

## Оговорки

- Замеры делались при живом трафике (в том числе при тестах и открытых вкладках) — цифры CPU
  немного завышены по сравнению с полностью пустым сайтом; память и диск стабильны.
- ВДС общий: приведённые доли — только для `oboz-web`, без nginx/других сервисов.
- После смены `cacheTtlSec` сервис нужно перезапустить (`sudo systemctl restart oboz-web`),
  иначе старый TTL останется в памяти процесса.
- Тариф и лимиты трафика у провайдера не известны; если у вас, например, 1 ТБ/мес, то ~30 ГБ
  лент — это 3 % лимита.
